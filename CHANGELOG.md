# Changelog

All notable changes to the `kinoa-dashboard` plugin.

Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versioning: [SemVer](https://semver.org/spec/v2.0.0.html). Consumers receive an update **only when `version` in [`plugin/.claude-plugin/plugin.json`](plugin/.claude-plugin/plugin.json) changes** — bump it (and add an entry here) as the final commit of every release PR, then tag the release commit on `main` as `vX.Y.Z`.

## [Unreleased]

### Added
- `kinoa-inapp-template-to-prefab`: milestone templates render their steps as a **horizontal scroll** of step cards (`MilestoneScroll` → `MilestoneViewport` → `MilestoneContent` → `MilestoneStep`), one `KinoaInAppMilestoneStepView` per step. The list opens on the first ready step, else the first locked step, else the last.
- Two **CTA modes**: a claim button on every step (`per_step`) or one CTA under the ladder that takes over the ready step's button (`single`). `plan --milestone-cta auto|per_step|single` (default `auto`: exactly one template CTA slot means `single`); the decision is written to `plan.milestone` and `report.milestone` (`cta_mode`, `cta_mode_source`, `collect_all`), and the skill's Phase 4 confirms with the developer when `auto` disagrees with the tip image.
- **Collect-all**: a button whose key or name matches `(?:^|[\s_-])(collect|claim|get)[\s_-]*all(?:$|[\s_-])` (whole segments; `budget_all` does not count) claims ready steps in one `CollectMilestonesAsync` call and is active only while it has a step to claim. Like `MilestoneMainButton`, it collects by its own click action: a free one takes only the ready steps whose own button is free; a billing / ad / link one runs its action first and then takes every ready step. Info / rules buttons (`custom` action or `info_button` role) never count as the step CTA.
- `KinoaInAppFeatureHooks.RunButtonAction` (`Func<InAppMessage, InAppCustomButton, Task<bool>>`; `generate --feature-action-runner Ns.Class.Method`): the game's own handler for a milestone button's billing / ad / link action; the step is collected only when it returns `true`. Unassigned, such buttons collect nothing and the hand-off carries the TODO. While a collect or the hook is running, milestone buttons ignore taps.
- Two new user-owned shared files, `Shared/KinoaInAppFeatureHooks.cs` and `Shared/KinoaInAppMilestoneStepView.cs`. Existing projects only **gain** these files on a re-run: `KinoaInAppHooks.cs` and `KinoaInAppItemView.cs` are never touched.
- `kinoa-inapp-template-to-prefab`: **missions UI**. A mission template's prefab now gets a tab per mission set (previous set first), a vertically scrolling list of mission cards (placement, text, sub-mission, status, progress, rewards, action, dismiss ×) ordered Reached → Active → Collected, and the combined progress bar (`ProgressBarState`) as a **milestone ladder** — the same horizontal scroll of `KinoaInAppMilestoneStepView` steps as a milestone template, ordered by `MilestoneNumber` (shown unless `progressBar.display` is `dont_show_at_all`). A card's Collect calls `CollectMissionsProgressAsync`, its Go raises the new `MissionCtaClicked` event, its dismiss × calls `DeleteMissionsProgress` (deletes the row's progress on the server). A bar step claims through the milestone click resolver: close closes, a free step calls `CollectMissionsMilestonesProgress`, a billing / ad / link step runs `KinoaInAppFeatureHooks.RunButtonAction` first and collects only when it returns `true`. **Reach all**, **Collect all** and **Collect all milestones** buttons are wired only when the template declares a button whose key or name says so (`report.mission_actions`); they bypass `KinoaUiService` (the view sends `in_app_click`, raises `ButtonClicked`, then runs the mission call; Collect all milestones goes through the same resolver with the milestone collect-all rule). Granting a collected row's or bar step's rewards and routing a Go tap are `TODO(kinoa-prefab)` items. New plan node bindings `tab_template` / `tab_part` / `mission_row_template` / `row_part`, node fields `feature_action` / `color` / `scroll_axis`, and `report.mission_actions` / `report.mission_geometry` (the prefab plan `schema_version` stays `"1.0"`). Two more user-owned shared files, `KinoaInAppMissionRowView` and `KinoaInAppTabView` (written when absent, like the other `Shared/` files).
- `kinoa-inapp-template-from-image`: layout artifact schema **1.1** (additive; a `1.0` artifact stays valid in both skills): for mission templates the vision pass records `feature.parts` / `row_parts` / `style` — the geometry and colours of the tabs, task list, one representative card and its inner parts, and the combined bar (bounded with its markers and rewards: it becomes the prefab's step ladder). Advisory like `feature.area_bbox`, never template elements. The prefab skill builds the missions look from it, with neutral defaults for any missing part (`report.mission_geometry.defaulted`), and offers the tip-image path B for a mission template whose artifact has none.

### Changed
- Milestone plans must be produced by this version. `generate` refuses a milestone plan without the `milestone` block / `MilestoneScroll` node (written before the scroll ladder) with `milestone_plan_outdated` — re-run `plan` for the template; nothing is written. Standard plans from 1.1.0 build unchanged.
- `kinoa-inapp-template-to-prefab`: the mission view no longer renders one row per `ActiveMissions` entry in a flat list. Mission plans must be produced by this version too: `generate` refuses a mission plan from before the tabs / cards / ladder tree with `mission_plan_outdated` (re-run `plan`; nothing is written). The scroll infrastructure is shared: the builder has one `scroll` / `viewport` / `scroll_content` binding set (wired by `WireScrollRects`), horizontal by default; the mission card list opts into vertical with the node field `scroll_axis: "vertical"`, which plans without it never carry — a milestone plan builds exactly as before. Standard and milestone views are unchanged byte for byte.

## [1.1.0] — 2026-10-14

### Added
- `kinoa-inapp-template-from-image`: turns a client mockup of an in-app pop-up (local file or URL; finished art or labelled wireframe) into a Kinoa in-app template. Vision analysis (element roles, normalized bboxes, feature-type detection with mockup-derived CTA menus) → deterministic builder (payload, validation, reuse matcher against the game's existing templates) → interactive confirmation page (overlay editor: include-gating, drag/resize, badge-click placement for any row without a box, bucket moves, CTA chip pickers, custom fields) → draft registration via the dashboard helper with the mockup attached as the template's **tip image** by default. Developer corrections ship to telemetry as deltas + a sha256 fingerprint — the image itself never leaves the machine.
- The **layout artifact** `<template_key>.layout.json` (contract: the skill's `references/layout-artifact.md`): written next to the template JSON after confirmation — per-element normalized top-left bboxes joined 1:1 with the payload keys, source-image pixel size + sha256, client-rendered zones, optional `feature.area_bbox`; elements with no confirmed position ship `bbox: null` + `unplaced: true`, never dropped. This is the input contract of `kinoa-inapp-template-to-prefab`. Builder subcommands: `layout` (confirmed envelope → artifact; `--build` fallback with an explicit pre-confirmation warning) and `validate --layout` (coordinate convention, ranges, the 1:1 join).
- Layout for templates already **on the dashboard** (`remap`): derives the artifact from the record's tip image — keys strictly the record's (never minted), a feature-type mismatch fails closed, element-level disagreements in either direction surface as a "tip image does not match" banner on the confirmation page, where unmatched slots can be placed by hand.
- `kinoa-dashboard-inapp-template`: admin CLI for in-app message templates (`/api/message_templates`): list / get / create (→ draft) / guarded update (draft-only, refuses on referenced templates or slot loss, `--dry-run`) / has-related. **No delete by design.** Tip image: URL inside the JSON body, or a local file uploaded as a separate image-only PATCH. `Key-Inflection: camel` is pinned on every call — without it the server silently drops camelCase fields.
- Auto-pagination for every listing endpoint across the four dashboard helpers (`kinoa-dashboard-event`, `kinoa-dashboard-player-fields`, `kinoa-dashboard-feature-settings`, `kinoa-dashboard-resource-template`). `--rows` is now the page size, not a global limit: when the server reports more records (`totalCount`) than one page holds, the next pages are fetched and merged, so the printed `response` always carries the full listing. The output gains `pages_fetched`, plus `truncated: true` when the merge had to stop early (a no-progress page before `totalCount`, or the page-safety cap) and `count_mismatch: true` when it assembled more elements than the final `totalCount` (overlapping/shifting page windows); a non-2xx page fails closed (`ok: false` + `failed_page`) — a partial merge is never presented as complete. `kinoa-dashboard-resource-template list` keeps a legacy single-page mode via an explicit `--page N`.
- `kinoa-inapp-template-to-prefab`: visualises a Kinoa in-app template as a Unity uGUI prefab inside the open Editor via the Unity MCP (hard gate; mcp-unity / unity-mcp / Unity-MCP detected by tool name). Probes existing popup prefabs for UI conventions, positions slots from the from-image skill's layout artifact `<template_key>.layout.json` (`plan --layout-artifact`; preferred — refused when its `template_key` differs, joined 1:1 on `(bucket, key)` with stale-artifact warnings, out-of-range element boxes rejected and out-of-range zone boxes dropped with a warning, `feature.area_bbox` places mission/milestone UI; a tip-image layout comes from that skill's remap-gated path B) or the raw `build_result.json` as a fallback, and generates a per-template `KinoaInApp<Pascal>View` (binds `InAppMessage`, lifecycle events, click routing through `KinoaUiService` when present), shared `KinoaInAppHooks` delegates (remote images / store price / resource icons — wired to existing game methods or left as `TODO(kinoa-prefab)`, never a new downloader), `KinoaInAppItemView`, and the Editor `KinoaInAppPrefabBuilder` with per-plan build reports. The planner keeps texts, buttons and zones apart. The panel spans every positioned element, so nothing clamps onto the art's edge. A de-overlap pass then moves default-positioned nodes to free space and trims boxes that only graze each other. It keeps intended overlays, such as a price on the CTA, badges, or zones on a task list, and reports the rest (`report.layout_adjustments`, `report.overlays`). Art is built behind controls and never takes clicks. The prefab root gets a `Canvas`, `CanvasScaler` and `GraphicRaycaster`, copied from a reference pop-up's root canvas or set to pop-up defaults (overlay, sorting order 100, scale with screen size at the design frame), and the hand-off asks the developer to align them. Offline tests: `test_inapp_prefab_{fixtures,style_probe,plan,codegen}.py`.

### Changed
- Milestone CTA menus (`features.milestone.mainActionTypes` / `milestonesActionTypes`) accept **nine** click actions — `custom` left the vocabulary (dashboard contract change; live-verified: create with it → 422 enumerating the nine). The builder derives milestone menus against the 9-action list, the confirmation page offers nine chips there (mission menus keep all ten), and legacy records carrying `custom` are stripped on remap/export instead of failing.
- The SDK sync planner's `listing_truncated` fail-closed exit is now a backstop: with auto-paginating helpers, a `totalCount`/`elements` gap signals a stale or hand-assembled listing file, and the guidance is to re-run the fetch, not to raise `--rows`. The planner additionally honors the helper's own flags — a listing carrying `truncated: true` / `count_mismatch: true` exits 2 with `listing_unreliable`.
- Workflow SKILL.md truncation guards rewritten accordingly (player-fields, events, feature-settings, resource-templates syncs + SDK dashboard sync troubleshooting).
## [1.0.0] — 2026-07-31

First pinned version. Everything below previously shipped unversioned (every `main` commit was a release).

### Added
- API-integration workflows (`kinoa-api-integration` orchestrator): credential setup (`kinoa-init`), player-fields sync, open-session runtime helper, event sync, feature-settings sync, resource-template registration, CSV→schema inference (`kinoa-csv-schema-infer`).
- Dashboard admin CLIs: `kinoa-dashboard-event`, `kinoa-dashboard-player-fields`, `kinoa-dashboard-feature-settings`, `kinoa-dashboard-resource-template`.
- SDK-mode dashboard sync (`kinoa-sdk-dashboard-sync`): consumes `kinoa-dashboard-manifest.json`, mirrors events / player fields / feature settings / resource templates onto the Dashboard; never deletes dashboard entities.
- Offline unit-test suite (`tests/`), including the boilerplate-consistency drift guard for the duplicated helper boilerplate.
